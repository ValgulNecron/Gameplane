# Implementation Plan: Install-Time Configuration

**Branch**: `006-install-time-config` | **Date**: 2026-08-25 | **Spec**: ./spec.md

## Summary

This feature enables operators to configure two critical Gameplane settings at install time via Helm values, eliminating post-deployment manual steps and solving the OIDC-only bootstrap problem. First (P1): OIDC role mapping via group claims, so the first OIDC user logs in with the correct dashboard role without running bootstrap-admin — and, per the maintainer's hybrid resolution of the FR-007/SC-007 tension, admins can subsequently manage those mappings through the dashboard with no Helm re-run and no API restart. Second (P2): default storage class for game-data volumes, so operators specify once at install time instead of editing every GameTemplate afterward.

**Technical approach**: Operator accepts two new Helm values—`operator.gameDataStorage.storageClassName` (propagated to operator flag `--game-data-storage-class`) and API-consumed Helm-supplied OIDC config (via existing `--oidc-*` flags expanded with `--oidc-groups-claim`, `--oidc-default-role`, and three per-role `--oidc-role-mapping-{admin,operator,viewer}` flags, each with `GAMEPLANE_OIDC_*` env fallbacks). Storage class defaults are injected after the PVC precedence chain (GameServer override > GameTemplate default > install-time default > cluster default). OIDC mappings are synthesized as a read-only "helm" provider at API startup (`HelmProviderName` in `api/internal/auth/registry.go`), coexisting with dashboard-managed providers — this provider itself remains immutable through the dashboard. **Hybrid role-mapping design (maintainer decision, binding, settled mechanism)**: Helm values *seed* the role mappings (satisfies FR-007/SC-003/SC-004 — OIDC-only installs need no admin account and no `bootstrap-admin` run). Admins can then override individual roles' group lists through the dashboard with **no new table and no migration**: the existing `"auth"` row in the `config` table (already read/written by `GET /admin/config` and `PUT /admin/config/{section}`, see `api/internal/auth/registry.go:179-185`) gains one optional sibling field next to `"providers"`, `helmOverride.roleMappings`, holding independently-optional `admin`/`operator`/`viewer` string lists (`{"providers":[...],"helmOverride":{"roleMappings":{"admin":[...],"operator":[...],"viewer":[...]}}}`). `helmOverride` is not a provider entry — the existing reserved-name guard on `"helm"` (`api/internal/handlers/auth_provider_secret.go:36`) is untouched. A new helper, `effectiveHelmPolicy(base *ProviderPolicy, ov *RoleMappings) *ProviderPolicy`, does per-role list replacement — for each of admin/operator/viewer, a non-nil override list replaces the Helm-seeded list for that role only (an empty non-nil list validly means "nobody maps to this role"); a nil override leaves the Helm-seeded list standing. The three roles resolve independently. The merge happens *before* resolution, so the existing, unmodified `computeRole` (`api/internal/auth/oidc.go:121`) is then called once against the merged policy and keeps its existing admin > operator > viewer first-match ordering and its existing tests — meaning a user who matches an overridden viewer group *and* a Helm-seeded admin group still resolves to admin, because the most privileged match wins after the merge, not before it. **SC-007 mechanism (verified, corrected)**: the registry's SHA-256-of-the-raw-row cache (`registry.go:172-186`) governs DB-defined providers only — `OIDCFor` short-circuits for the helm provider and returns `r.legacy` immediately, before `snapshot()`, before the hash, before the cache (`registry.go:224-232`), and `r.legacy` is a single `*OIDC` built once at API startup (`api/cmd/main.go:127`) and held for the process lifetime, so that cache never sees a helm-provider edit. Instead, the helm path reads `helmOverride` fresh on every login: `registry.go:152-153` already calls `legacy.AttachStore(store)`, so the helm provider already holds a reference to the config store; role resolution for the helm provider reads the `"auth"` row's `helmOverride` at login time, builds the merged policy via `effectiveHelmPolicy`, and calls the existing `computeRole`. Because this read happens per login attempt rather than being cached, an admin's edit lands on the very next login with no API restart and no `helm upgrade` — that per-login read is what delivers SC-007, and no new caching layer is introduced. On a later `helm upgrade`, only the Helm-seeded lists change; a role carrying a DB override keeps it. Exactly one new HTTP route is added: `DELETE /admin/config/auth/role-mappings/{role}`, removing one role's override so it reverts to the Helm-seeded value; it is mounted under the existing `/admin/config` prefix and inherits the same `config:manage` RBAC gate as every other config route (`api/internal/rbac/rbac.go:170`). Provenance is key-presence only — there is no separate provenance field: a role key present in `helmOverride.roleMappings` means that role is overridden, and a role key absent from it means the role's mapping comes from the Helm seed; the dashboard derives provenance and gates the reset action from that presence check against the existing `GET /admin/config` response, with no new field added to it. Every write of `helmOverride` (via the existing `PUT /admin/config/auth`) and every reset (via the new `DELETE`) is admin-gated and audited through the existing `Auditor.WriteSync(ctx, method, path, target, reason string, status int)` call, using one consistent reason-string format stated once (see Slice 5). `groupsClaim` and `defaultRole` remain Helm-only and are not overridable in v1. Error states (missing StorageClass, misconfigured OIDC) are surfaced in GameServer status conditions and the dashboard config view. `bootstrap-admin` remains the unaffected break-glass path (FR-013).

## Complexity Tracking

No constitutional violations; this section is intentionally empty. ### Slice 5: `helmOverride` Overlay for Admin-Managed OIDC Role Mapping Overrides (Hybrid Design, Dependency on Slice 4)
- **What**: Implement the hybrid role-mapping overlay on the settled mechanism — **no new table, no migration**. (1) **Storage shape**: the "auth" config row's JSON gains one optional sibling field next to `"providers"`: `helmOverride.roleMappings`, with independently-optional `admin`/`operator`/`viewer` string lists (M2). `helmOverride` is not a provider entry; the reserved-name guard on `"helm"` is unchanged. This is read and written through the *existing* `GET /admin/config` and `PUT /admin/config/auth` handlers in `api/internal/handlers/config.go` — no new write route. (2) **Merge helper**: add `effectiveHelmPolicy(base *ProviderPolicy, ov *RoleMappings) *ProviderPolicy` in `api/internal/auth/oidc.go` — for each of admin/operator/viewer independently, a non-nil override list *replaces* the Helm-seeded list for that role (a non-nil empty list validly means "nobody"); a nil override leaves the Helm-seeded list standing (M3). (3) **Resolution — the SC-007 mechanism (corrected)**: the hash-based registry cache (`registry.go:172-186`) invalidates on a config-row edit for DB-defined providers, but it never runs for the helm provider — `OIDCFor` short-circuits and returns `r.legacy` immediately for `HelmProviderName`, before `snapshot()`, before the hash, before the cache (`registry.go:224-232`), and `r.legacy` is a single `*OIDC` built once at API startup (`api/cmd/main.go:127`) and held for the process lifetime. So the cache cannot be what delivers SC-007 on the helm path. Instead, because `registry.go:152-153` already calls `legacy.AttachStore(store)`, the helm provider already has the store; role resolution for the helm provider reads `helmOverride` from the `"auth"` row at login time, builds the effective policy via `effectiveHelmPolicy`, and then calls the existing, **unmodified** `computeRole` once — its admin > operator > viewer first-match ordering and its existing tests are untouched (M4). Because this read happens per login attempt rather than being cached, an edit lands on the next login with no API restart and no `helm upgrade` — that is what delivers SC-007, with no new caching layer introduced. Document explicitly: because the merge happens per-role before `computeRole` runs, a user matching an overridden viewer group *and* a Helm-seeded admin group still resolves to admin. (4) **Provenance in GET — key presence only**: `getAll()`'s "auth" response is unchanged in shape; no new provenance field is added. A role key present in `helmOverride.roleMappings` means that role is overridden; a role key absent from it means the role's mapping comes from the Helm seed. The dashboard derives provenance and gates the reset action from that presence check. (5) **New reset route**: `DELETE /admin/config/auth/role-mappings/{role}` (the only new route in this slice) removes one role's override, restoring the Helm-seeded value; mounted under the existing `/admin/config` prefix, inheriting the existing `config:manage` RBAC gate (`api/internal/rbac/rbac.go:170`) — no separate middleware wiring needed. (6) **Audit events**: every `PUT /admin/config/auth` that changes `helmOverride` and every `DELETE` reset calls the existing `Auditor.WriteSync(ctx, method, path, target, reason string, status int)`. `MountConfig` gains an `*audit.Auditor` parameter as its third parameter — `MountConfig(r chi.Router, store *db.Store, auditor *audit.Auditor, helmOIDCPresent bool)` (precedent: `MountCapture` at `capture.go:55`) — so its call site in `api/cmd/main.go` (currently `handlers.MountConfig(p, store, oidcAuth != nil)` at `main.go:245`) changes too (C6). Canonical reason strings, target=`<role>` in both cases: set — `"oidc role mapping override set: role=<role> groups=<comma_joined_or_none>"`; reset — `"oidc role mapping override reset: role=<role>"`. (7) **Upgrade semantics (M9)**: on `helm upgrade` with changed OIDC values, only the Helm-seeded lists change; a role carrying a `helmOverride` entry keeps it — the reset route is the only way back to the Helm-declared value. Add unit tests for `effectiveHelmPolicy` (override replaces, nil leaves standing, empty-non-nil means nobody, independent per-role resolution, privileged-match-wins-after-merge per M4) and envtest cases for the extended config endpoint (provenance in GET, PUT persisting helmOverride, next-login effect with no restart) and the new reset route (RBAC gate, round-trip, reverts to Helm seed, audit event per mutation).
- **Touch Points**: `api/internal/auth/oidc.go` (`effectiveHelmPolicy` + resolution call site), `api/internal/auth/registry.go` (helmOverride field on the auth config JSON), `api/internal/auth/oidc_rolemap_test.go` (merge unit tests), `api/internal/handlers/config.go` (auditor param on MountConfig, new DELETE role-mappings reset route — no provenance field added to getAll), `api/internal/handlers/config_envtest_test.go` (extended envtest cases).
