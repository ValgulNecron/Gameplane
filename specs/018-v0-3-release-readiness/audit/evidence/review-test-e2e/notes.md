## Candidate findings

### C-e2e-01: `fastGameSet` (default game scope) includes three games that `buckets.sh` deliberately excludes from CI as heavy/oversized — and the "fast set" is defined three inconsistent ways across the codebase

- **Location**: `test/e2e/gamebot_helpers_e2e_test.go:24-32` (`fastGameSet` var); `test/e2e/buckets.sh:214,230,240` (bot-heavy exclusion comments); `test/e2e/internal/specs.md:295-299` vs `:345-354`
- **Category**: docs-drift / correctness (latent)
- **Suggested severity**: S3
- **Observation / repro**: There are three different, disagreeing definitions of "the fast set" in this codebase:
  1. `buckets.sh`'s actual `bot-fast` bucket (what CI's `e2e-game-bot` job runs, via `RUN_REGEX="$(./test/e2e/buckets.sh regex bot-fast)"`, `ci.yaml:1112`): exactly 3 tests — `TestGameServer_MinecraftJavaBot_Joined`, `TestGameServer_TerrariaBot_Joined`, `TestGameServer_GarrysModBot_Query` (games: minecraft-java, terraria, garrys-mod).
  2. `internal/specs.md`'s own "## Why the fast set is small" section (line 347): *"Four games cover the essential depth variety"* — minecraft-java, terraria, **factorio**, garrys-mod — even though the "### E2E test registration" section 50 lines above it (line 295-299), in the same file, correctly lists only the 3 CI-run tests and does not mention factorio.
  3. The code's `fastGameSet` var (`gamebot_helpers_e2e_test.go:29-32`), which is what actually governs `skipUnlessGameInScope`'s default (`parseGameScope`, `:55` — `games == ""` returns `fastGameSet`): `"minecraft-java", "terraria", "factorio", "garrys-mod", "tmodloader", "beammp"` — six games. The preceding comment (`:25-28`) still says *"These four cover..."* and describes only four, not six.

  Crucially, `factorio`, `tmodloader`, and `beammp` are each explicitly bucketed under `bucket_bot_heavy` in `buckets.sh` with stated resource-exhaustion reasons — e.g. `buckets.sh:240`: `TestGameServer_TModLoaderBot_Query: Multi-GB tModLoader/.NET image download and persistent mod storage`, `buckets.sh:230`: `TestGameServer_BeamMPBot_Query: 5Gi storage + vehicle assets overhead (exceeds runner disk)`, `buckets.sh:214`: `TestGameServer_FactorioBot_Query: Modest alone (5Gi storage, 1Gi memory) but cumulative with heavier games` — and `bucket_bot_heavy`'s own header (`buckets.sh:197-207`) states this bucket is *"DELIBERATELY never run in CI — not on PRs, not nightly, not on `schedule:`, not via `workflow_dispatch:`... only a maintainer hand-run with `GAMEPLANE_E2E_GAMES=all`"*.

  Because `bucket_bot_fast` (the only bucket CI's `e2e-game-bot` job's `-run` regex selects) omits `TestGameServer_FactorioBot_Query`/`TestGameServer_TModLoaderBot_Query`/`TestGameServer_BeamMPBot_Query` entirely, today's CI run is safe: those three test *functions* are never invoked by `go test -run "^(TestGameServer_MinecraftJavaBot_Joined|...)$"`, so `fastGameSet`'s contents never actually execute in the pipeline described in `ci.yaml`. The bug is latent, not active.
- **Expected**: `fastGameSet` (the variable that decides which games run when `GAMEPLANE_E2E_GAME_BOT=1` and `GAMEPLANE_E2E_GAMES` is left unset — the exact invocation shape documented for a maintainer hand-run of a *subset*, e.g. `internal/specs.md:367`'s `GAMEPLANE_E2E_GAMES=all` example implies the *unset* case is meant to be the safe/cheap default) should contain only the games that are actually safe to run without the `GAMEPLANE_E2E_GAMES=all` heavy-resource opt-in — i.e. the same 3 (or, if factorio is intentionally meant to be "fast-but-not-CI-executed", that distinction needs to be stated, not silently contradicted).
- **Actual**: `fastGameSet` silently includes 3 heavy-bucketed games. A maintainer (or CI change) that runs `GAMEPLANE_E2E_GAME_BOT=1 GAMEPLANE_E2E_REUSE_CLUSTER=1 ... go test -tags=e2e ./...` without an explicit `-run` filter and without setting `GAMEPLANE_E2E_GAMES` — e.g. trusting the "unset = fast set" contract stated in `parseGameScope`'s own doc comment (`gamebot_helpers_e2e_test.go:47-49`: *"unset => the fast set"*) — would have `TestGameServer_TModLoaderBot_Query` and `TestGameServer_BeamMPBot_Query` proceed past their `skipUnlessGameInScope` gate and attempt multi-GB SteamCMD/.NET downloads, exactly the outcome `buckets.sh` says must never happen outside an explicit `GAMEPLANE_E2E_GAMES=all` hand-run.

### C-e2e-03: Login-budget bookkeeping for `api-roles` is wrong in two places — `buckets.sh`'s own running tally omits a test's admin login, and the `e2e-test-authoring` skill's stated ceiling is already exceeded

- **Location**: `test/e2e/buckets.sh:118-136` (the `spends 4` / `bringing api-roles to 5` / `bringing api-roles to 6` comment chain) vs `test/e2e/api_owner_collab_e2e_test.go:29-30,42-43`; `.claude/skills/e2e-test-authoring/SKILL.md` ("Login budget per bucket" section: *"Keep api-auth ≤ ~8 logins, api-roles ≤ ~5."*)
- **Category**: docs-drift
- **Suggested severity**: S3
- **Observation / repro**: `bucket_api_roles()` (`buckets.sh:139-148`) currently lists 7 tests: `TestAPI_CustomRole_Lifecycle`, `TestAPI_BuiltinRole_Immutable`, `TestAPI_PerNamespaceBinding_GrantsScopedAccess` (each 1 admin login, per `api_roles_e2e_test.go:23,124,150`), `TestAPI_OwnerCollaboratorAccess` (1 admin login — its own doc comment at `api_owner_collab_e2e_test.go:29-30` says *"Login budget: 3 non-admin logins (owner-user, collab-user, plus the admin setup login...)"*, and `:42-43` shows `envInstance.BootstrapAdmin(t, adminUsername, adminPassword)` / `envInstance.APIClient(t, adminUsername, adminPassword)`), `TestAPI_AuthConfig_RoleMappings` (1 admin login, `api_auth_e2e_test.go:413,415`), `TestAPI_OIDCHelmOverride_EffectiveAtLoginTime` (1 admin login, `:970,971`), and `TestAPI_ThemePreferences` (1 admin login + 1 fresh-user login, `api_theme_preferences_e2e_test.go:143-144`). That is **7** logins against the shared `e2e-admin` username, not the 6 the running comment arrives at.

  Tracing `buckets.sh`'s own comment chain: *"[AuthConfig_RoleMappings] lives here, in a bucket that spends 4"* (`:121`) → *"[OIDCHelmOverride] costs +1 admin login, bringing api-roles to 5 (up from the previous 4)"* (`:130`) → *"[ThemePreferences]... bringing api-roles to 6"* (`:136`). This chain is self-consistent (3 base tests + AuthConfig=4 → +OIDCOverride=5 → +ThemePreferences=6) but at no point adds `TestAPI_OwnerCollaboratorAccess`'s 1 admin login, even though that test is a live member of `bucket_api_roles()` and its own doc comment states it spends one. The tracked total (6) is one short of the real total (7).
- **Expected**: A maintainer reading `buckets.sh:136` ("bucket spends 6") and the skill's stated ceiling ("api-roles ≤ ~5") would each independently (and wrongly) conclude there is headroom to add more admin-login-consuming tests to `api-roles`.
- **Actual**: The bucket already sits at 7 real admin logins — at the shared, unqualified "~7 admin logins ≈ the per-user burst" ceiling stated in `buckets.sh`'s own top-of-file header (line 31) and in this task's own "extra focus" framing, i.e. already at its slack-free maximum, not comfortably under it. Because `APIClient`'s retry-with-backoff (`env.go`) absorbs a 429 rather than failing the test outright, this is not (yet) an active CI failure — but the *tracked* number both docs rely on to decide "is there room for one more test" is wrong by one full login in the direction that invites a future regression: the next test added to `api-roles` on the strength of either stale number would push the bucket to 8, past every documented ceiling, and the per-user burst (6, refilling 3/min) would then need retries to absorb a 2-login deficit instead of 0-1.
